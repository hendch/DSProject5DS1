02What is not working

Ordered by what would hurt a live demo first.

Blocks the demo

  • GitHub is not connected blocker

    The watcher, alerts and automatic investigations exist, but no account has been connected, so none of it has run against the real GitHub API. Real data can differ from what the tests assume, for example log download permissions on Actions runs.

    Fix: create a GitHub OAuth App with Device Flow enabled and paste its Client ID in Settings, or paste a personal access token. Follow hendch/DSProject5DS1, push a commit that breaks a test, and check that the red alert and an RCA run appear within a minute.

  • Drift Detection cannot start blocker

    Omar's repository ignored every folder called data/, which also hid the agent's own source package agents/drift_detection/data. Without it, the agent cannot load, and 18 of its tests are skipped.

    Fix: Omar commits that package (and narrows the ignore rule), then runs drift-agent init once to train the first model.

  • Dependency Resolver runs on its fallback degraded

    It wants the OpenTofu CLI to build the real dependency graph. Without it, it reads the .tf files with a static parser. The Guardrail treats fallback output as less reliable and raises its risk one level. It also only runs when a trigger includes a folder of .tf files, which today means the demo scenario only.

    Fix: install OpenTofu and put tofu on the PATH.

A buyer would notice

  • No real user accounts

    Who you are is picked from the "Acting as" menu. The rules "you cannot approve what you triggered" and "two different people for high-risk production changes" work on names, not on verified identities. Anyone who can open the dashboard can approve as anyone. The API also accepts requests from any origin.

    Fix: tie each person to their GitHub sign-in and restrict the API to the dashboard's origin.

  • Nothing is written back to GitHub

    An approved Code Reviewer patch is recorded as "Dry run: would push bot/minimal-fix and open a draft pull request". Setting ORCHESTRATOR_GITHUB_PUBLISH=true does not help yet: it reports failure because publishing was never implemented. Review findings are not posted as PR comments either.

    Fix: push the patch branch and open the draft PR through the GitHub API with the signed-in token, and post findings as a PR review.

  • Watching is by polling, and partial

    GitHub cannot reach localhost, so the app asks GitHub every 60 seconds instead of receiving webhooks. It sees the 25 latest commits on the default branch, other branches only through their CI runs, and the 20 most recently updated PRs. A push with no CI and no PR is listed but not analysed.

  • Merge and drift are not triggered by GitHub

    Only failed CI and pull requests start runs automatically. The Merge Assistant runs on a demo repo unless the API is given a local repository path.

  • Local only

    The app runs on one machine with an embedded PostgreSQL. It is not deployed. The free Hugging Face tier has rate limits; when a model fails, agents fall back to rules and the run is marked "degraded".

Small things

  • Agent registry shows the wrong model for Drift

    It shows the shared Llama profile. The drift agent actually reads XAI_MODEL and uses Grok.

  • Settings and Agent registry load slowly

    They show loading placeholders for a few seconds on first open.

  • Desktop notifications not tested

    The in-app preview browser blocks them. The in-page toasts work.

  • Work is not pushed

    The orchestrator branch exists only on Rayen's machine. An older commit on guardrail-agent (2455c70) still carries an AI co-author line, which needs a force push to remove.

03How it fits together

Agents never call each other. The orchestrator calls each one through a small adapter, passes what earlier steps found to later steps, and publishes every proposal as an event. The Guardrail decides on every proposal before anything is executed, and every decision lands in a tamper-evident audit log.

Why this shape. Each teammate's agent stays a separate module with its own fallback. The orchestrator is plain code, not an LLM, so a run always takes the same path for the same input and can be replayed from the database. LLMs are used where judgement helps: diagnosing, reviewing, explaining, and a second opinion in the Guardrail.

04Life of a run

A run is one trigger and everything that follows from it. Its state lives in orchestrator.runs, so a restart picks up where it stopped.

stateDiagram-v2
  [*] --> received
  received --> running: route chosen
  received --> needs_triage: no confident route
  needs_triage --> running: a person picks the route
  running --> waiting_approval: proposals published
  running --> executing: nothing to approve
  waiting_approval --> executing: every proposal decided
  executing --> completed
  running --> failed: unexpected error
  completed --> [*]

Example: the failed IAM deploy

  1. Sami starts the "Failed deploy: IAM cycle" scenario. The trigger is a deploy failure, so the rules pick the route deploy_failed: Dependency Resolver, then Diagnostic / RCA.
  2. The Dependency Resolver finds a cycle between aws_iam_role, aws_eks_cluster and aws_iam_role_policy and proposes a fix. Like every agent, it labels its own risk "low".
  3. The Guardrail does not trust that label. It sees iam in the payload, a permissions change, and raises the risk to high. The policy rule high_always_human holds it for one approval.
  4. The RCA agent ranks the causes of the log. That is advice only, so the Guardrail approves it automatically.
  5. Sami tries to approve the fix and gets refused: you cannot approve what you triggered. Ines approves it.
  6. The executor records "skipped": the fix is an explanation that the owner applies by hand. The run completes, the orchestrator's model writes a short summary, and each step is in the audit log.

05Routing

Choosing which agents handle a trigger goes down a ladder, and stops at the first step that is sure enough.

StepHow it decidesWhen it is used
1. RulesThe trigger type (failed CI, pull request, scenario), or keywords in the text such as "terraform", "merge", "drift".Almost always. Every GitHub trigger is routed here.
2. LLM triageThe orchestrator's model reads free text and returns a route and a confidence.Free-text requests with no matching keyword. Accepted at confidence 0.7 or above.
3. Human triageThe run waits on the Triage page until a person picks the route.When the model is unsure or unavailable.

Routes

RouteSteps, in order
build_failedDiagnostic / RCA
deploy_failedDependency Resolver → Diagnostic / RCA
merge_requestedMerge Assistant
pull_requestDiagnostic / RCA only if the PR's tests failed → Code Reviewer
drift_checkDrift Detection → Diagnostic / RCA only if drift looks like a pipeline bug

Conditional steps read the facts earlier steps left behind. For a failing PR, for example, the RCA diagnosis is passed to the Code Reviewer so its review can mention why the tests broke.

06The agents

Each agent can propose only the action types listed for it. The Guardrail rejects anything else.

Input

How
Strips colours and timestamps and keeps error lines with a little context (up to 3,000 characters). 07The Guardrail

Every proposal is checked in three layers. The rule that holds them together: each layer can make a decision stricter, and none can make it looser.

Layer 1: risk from evidence

The proposal starts at the risk the agent declared. The Guardrail then scans what the action actually touches and raises the level when it finds:

Signal in the payloadRaises to
prod, productionhigh
Destructive words: destroy, delete, drop table, truncate, rm -rf, terminatehigh
Permissions and security: IAM, KMS, secrets, security groups, firewalls, roleshigh
Billable infrastructure: GPUs, instances, RDS, clusters, NAT gateways, autoscalingmedium
Infrastructure state: backend, tfstate, state lockmedium
The agent fell back to rules or static analysisone level up

Advice-only actions skip this scan, because approving them changes nothing.

Layer 2: the policy

Written in Rego and evaluated by Open Policy Agent. Rules are tried from top to bottom and the first match wins.

RuleWhenDecision
agent_not_allowed_actionThe agent proposed an action it is not allowed toreject
prod_high_two_personHigh risk in productionhold · 2 people
high_always_humanHigh risk anywhere elsehold · 1 person
advisory_onlyAdvice: rank_causes, review_code, drift_reportauto-approve
prod_requires_humanAny other change in productionhold · 1 person
staging_medium_humanMedium risk in staginghold · 1 person
low_risk_autoLow risk in dev or stagingauto-approve
dev_medium_autoMedium risk in devauto-approve
default_holdNothing matchedhold · 1 person

Layer 3: the LLM judge

For changes the policy did not reject, a separate model reads the proposal and the evidence and says whether it looks risky. It can turn an automatic approval into a hold (rule llm_escalation), never the reverse. If the model is unreachable, the policy decision stands. The judge is Qwen 2.5 7B, a different model family from the agents it checks.

Approvals

  • The person who triggered a run cannot approve its proposals (the API answers 403).
  • A person cannot vote twice on the same proposal (409).
  • Pending approvals expire after 4 hours and count as rejected.
  • Every decision is written to reasoning_logs. Each row includes the hash of the row before it, so changing or deleting a row breaks the chain. The Audit page checks the chain and shows whether it is intact.

08After approval

Each decided proposal goes to an executor once. The result is stored, so running the executors again never repeats an action.

ActionWhat happens when approved
rank_causes, review_code, drift_reportnot needed Advice only.
propose_fixskipped The fix is an explanation. The owner applies it by hand.
flag_conflictskipped A person merges. The assistant never does.
propose_patchdry run Records the branch and draft PR it would open. Real publishing is not built.
promote_model, rollback_modeldone The drift agent applies it (once the agent can run).
Anything rejected or expiredskipped Nothing is executed. The drift agent is told about rejections.

09GitHub

Connecting

In Settings, "Sign in with GitHub" uses GitHub's device flow: the app shows a short code, you approve it on github.com, and the app receives a token. This needs a GitHub OAuth App, created once, with Device Flow enabled. The other way is to paste a personal access token. Then you choose which repositories to follow on the Repositories page.

What it reacts to

On GitHubIn OpsAgents
A commit's CI passesGreen status on the commit in Activity
A commit's CI failsCritical alert. The failing job's log goes to the RCA agent automatically.
CI passes again after a failure"CI is green again" alert
A PR is opened or gets new commitsInfo alert. The Code Reviewer reviews it automatically, with RCA first if its tests failed.
Token rejected, rate limit hit, repo unreadableAlert that points to Settings or Repositories

The first sync of a repository only records its history, so old failures do not raise alerts. Alerts are de-duplicated, so a failure is reported once. Automatic investigation can be turned off in Settings. Logs have secrets removed before they are stored or sent to a model.

10Models

Every agent has its own model profile in .env (<AGENT>_LLM_MODEL and related settings) and falls back to the shared default. All models are called through one OpenAI-compatible client.

Used byModelProviderWhy this one
Orchestrator, Dependency Resolver, Merge AssistantLlama-3.1-8B-InstructHugging FaceFast and cheap. Their tasks are short: classify, explain, summarise.
Diagnostic / RCADeepSeek-R1-Distill-Qwen-7BHugging FaceA reasoning model. Finding a root cause means weighing log lines against documents step by step.
Guardrail judgeQwen2.5-7B-InstructHugging Face (Featherless)A different family from the agents it checks, so it is less likely to share their blind spots. Reliable at structured JSON.
Code Reviewergrok-4.20-0309-non-reasoningxAIThe reviewer needs tool calls. The Hugging Face coder models tried did not support them.
Drift Detectiongrok-4.20-0309-reasoningxAIOmar's original setup.

When a model fails

  • Each call is retried twice. After a failure, that model is skipped for 30 seconds so a dead provider does not slow every run.
  • When a model is unavailable, the agent switches to its rule-based fallback, and the step is marked "degraded" on the run page.
  • Reasoning output (<think> blocks) is stripped, and JSON is extracted even when a model wraps it in prose. RCA turns JSON mode off, because DeepSeek-R1 answered with nothing in JSON mode.

11Data and plumbing

Everything lives in one PostgreSQL database, set up by numbered migrations 001 to 006 (python -m shared.migrate).

WhereWhat
events, event_receiptsThe event bus. Publishing and logging happen in one transaction. Consumers are woken by LISTEN/NOTIFY and keep one receipt per event. A failed event is retried 30 seconds later, with growing delays, and marked dead after 5 attempts.
approvalsGuardrail decisions and votes
reasoning_logsThe hash-chained audit log, append-only
orchestrator.*Runs, their steps and their actions
knowledge.documentsThe RCA knowledge base, as pgvector embeddings (BAAI bge-small-en-v1.5, 384 dimensions)
github.*Followed repos' commits and PRs, plus what has already been alerted on
alerts, app_settingsNotifications and settings such as the OAuth Client ID
driftThe drift agent's batches, runs and model versions

For development and tests, pgserver starts an embedded PostgreSQL 16 with pgvector, so no installation is needed. The policy runs on a local OPA binary in .tools/.

12Running it

Once, in the project folder:

pip install -e ".[dev]"

Start everything (database, policy engine, agents, GitHub watcher, dashboard) and open localhost:8080:

python -m app

Tests:

pytest -q

Add ?mock=1 to the dashboard URL to try the interface with sample data and no backend.
