OpsAgents: a guarded multi-agent assistant for DevOps and MLOps

Five specialist AI agents diagnose failed builds, review pull requests, untangle infrastructure, resolve merge conflicts and watch models for drift. An orchestrator coordinates them, and a guardrail makes sure no change reaches production without the right human approval.

1Problem and targeted objectives

The problem

Teams that ship software and machine learning models lose hours to the same incidents: a CI build fails and someone has to dig through a long log; an infrastructure deploy fails on a dependency cycle; two branches conflict; a pull request quietly leaks test data into training; a model in production degrades because its input data changed. Each incident needs a specialist, and they tend to happen at the worst time.

AI agents can do much of this diagnosis. Letting them act on their own is risky, though: an agent that edits IAM permissions or rolls back a production model without oversight can cause more damage than the incident it was fixing.

Target users

  • Small DevOps and platform teams without round-the-clock specialists.
  • Data science teams that deploy models and own their pipelines.
  • Team leads and reviewers who approve changes and need to know why each one was proposed.

Main objective

Cut the time from "something broke" to "we know why and have a fix", while every change that carries risk stays under human control and leaves an auditable trail.

Specific objectives

  1. Diagnose failed builds automaticallyA ranked list of root causes, with the evidence each one relies on, within a minute of a failed CI run.
  2. Review every pull request for ML mistakesData leakage, unsafe preprocessing and lint issues, with a minimal fix proposed.
  3. Cover the rest of the delivery chainInfrastructure dependency cycles, merge conflicts and model drift, each handled by a dedicated agent.
  4. Never let an agent make a risky change aloneEach proposal is risk-scored, checked against a written policy and held for one or two human approvals when needed.
  5. Make every decision traceableA tamper-evident audit log of decisions, plus LangSmith traces of every agent step and model call.
  6. Keep working when an AI model failsEvery agent has a rule-based fallback, and the run is marked "degraded" rather than failing.

How the solution addresses it

OpsAgents connects to the team's GitHub repositories. When CI fails or a pull request opens, the orchestrator sends the right specialists. Their findings arrive as proposals, never as direct actions. The Guardrail scores each proposal's real risk and applies the team's policy. Advice and low-risk changes go through at once. Risky changes wait in an approval queue on the dashboard, where the person who triggered the run cannot approve it themselves. Everything is recorded.

2Multi-agent architecture

The system is an orchestrator–worker design with a separate supervisor (the Guardrail). Worker agents never call each other. The orchestrator calls them in order, passes what earlier agents found to later ones, and publishes each proposal as an event on a PostgreSQL event bus. The Guardrail consumes those events and decides. All components share one PostgreSQL database and one Python environment.

Guardrail

Rayen
Objective
Make sure no agent makes a risky change on its own (O4), and record every decision (O5).
Responsibilities
Validate every proposal; compute its real risk from evidence; apply the policy; ask an LLM judge for a second opinion; open approvals and enforce who may approve; expire stale approvals; write the hash-chained audit log.
Model
Qwen 2.5 7B Instruct (Hugging Face, via Featherless). It belongs to a different model family from the agents it checks, so it is less likely to share their blind spots, and it is reliable at strict JSON. The judge can only make a decision stricter, never looser.
Tools
risk scannerOpen Policy Agent (Rego)LLM judgeapprovals storehash-chained audit logapprovals API

How the Guardrail decides

  1. Risk from evidence. Every agent labels its own proposal "low". The Guardrail scans what the proposal actually touches and can only raise the risk. Production, destructive operations and IAM/secrets raise it to high; billable infrastructure and state files raise it to medium; output produced by a fallback raises it one level.
  2. Policy. Rego rules evaluated by OPA, first match wins. An agent proposing an action it is not allowed to is rejected. High risk in production needs two different people. Other high-risk changes need one. Advice is approved automatically. Low risk outside production is approved automatically. Anything unmatched is held (fail closed).
  3. LLM judge. Turns an automatic approval into a hold when it judges the change risky. If the model is unreachable, the policy decision stands.

How information flows

  • One id per incident. Each run's id is the correlation id on every event, approval, audit row and LangSmith trace, so the whole story of an incident can be followed.
  • Facts between agents. Agents leave facts for later steps. The RCA diagnosis of a failing PR is handed to the Code Reviewer, so the review can say why the tests broke. If Drift Detection classifies drift as a pipeline bug, it triggers an RCA step.
  • Proposals as events. Agents never act. Their output becomes events on the bus. The Guardrail answers with approval events, and the orchestrator picks up decisions and runs the executors.
  • Reliable delivery. Events are written in the same transaction as their log entry. Each consumer keeps a receipt per event. Failed events are retried with a growing delay, and marked dead after five attempts.

2bMonitoring the agents with LangSmith

A multi-agent system is hard to debug from logs: when a run gives a poor answer, you need to know which agent produced it, what that agent's model was asked, what it answered and how long it took. We integrated LangSmith, LangChain's tracing and evaluation platform, for this. Our agents do not use LangChain; LangSmith's SDK traces any Python code.

What is traced

Each orchestrator run becomes one trace, with a span per agent step and each model call nested inside its agent:

run: Failed deploy: IAM cycle              tags: orchestrator · metadata: run_id, route
├── Dependency Resolver                    status, summary, proposals
│   └── llm:dependency_resolver            prompt, answer, tokens, latency
├── Diagnostic / RCA
│   └── llm:diagnostic_rca                 DeepSeek-R1 call
└── (Code Reviewer, for pull requests)     runs in its own process and joins this trace
    └── llm:code_reviewer × N              one span per tool-calling turn
guardrail: dependency_resolver/propose_fix  risk, decision, rule, LLM verdict
└── llm:guardrail
execute and summarise                      executor results, LLM summary
└── llm:orchestrator

All traces of a run share a thread_id equal to the run id, so LangSmith groups the agents, the Guardrail's decisions (which happen asynchronously) and the execution after approval into a single thread.

How it is built

  • shared/tracing.py holds the integration. Tracing is on only when LANGSMITH_TRACING=true and an API key is set. Otherwise every helper does nothing, so the app runs the same without an account.
  • Every model call in the system goes through one client in shared/llm.py, which is wrapped with LangSmith's wrap_openai. The Code Reviewer and Drift Detection agents have their own clients, which are wrapped the same way.
  • The Code Reviewer runs as a separate process. The orchestrator passes it the parent trace's headers, so its spans attach to the right run.
  • The dashboard's Settings page shows whether tracing is on and which LangSmith project it writes to.

What it gives us

QuestionWhere the answer comes from
Which agent is slowest, or costs the most tokens?Latency and token counts per span, filtered by agent tag
Why did a run give a wrong diagnosis?The exact prompt, retrieved documents and answer of that model call
How often does each model fail and fall back to rules?Error rate per agent tag
Why was this proposal held for approval?The Guardrail span: risk, matched rule and LLM verdict
Two kinds of monitoring. The hash-chained audit log answers "what was decided, by whom, and has anyone altered the record?". LangSmith answers "how did each agent and model behave?". The first is for accountability, the second for debugging and improving the agents.

Status: integrated and covered by unit tests; tested with tracing switched on, offline. Live traces start as soon as the team's LangSmith API key is added to .env.

3Prototype demonstration

The prototype runs locally with one command (python -m app). That starts the database, the policy engine, the agents, the GitHub watcher and the dashboard at localhost:8080. The dashboard has 14 pages: Home, Activity, Runs, run detail, Approvals, Triage, Alerts, four Analytics views, Agent registry, Audit log, Repositories and Settings.

Main technical choices

  • Deterministic orchestrator, LLMs inside the agents. Routing and state live in code and in the database, so runs are repeatable, resumable after a crash and easy to test. LLMs are used where judgement adds value.
  • Different models for different jobs. A reasoning model for root causes, a tool-calling model for code review, a small fast model for short tasks, and a different family for the judge.
  • Policy as code. The approval rules are written in Rego and evaluated by Open Policy Agent, so they can be read, tested (20 policy tests) and changed without touching the agents.
  • PostgreSQL for everything. Records, the event bus (LISTEN/NOTIFY), the vector store and the drift data share one database, set up by six numbered migrations. That means one system to run and back up.
  • Graceful degradation. Each agent has a rule-based fallback, failing models are skipped for 30 seconds, and the Guardrail treats fallback output as less trustworthy.

Benchmark: 64 cases with known answers

To measure the agents rather than demo them, we built a separate benchmark repository (opsagents-bench). It contains a small churn-model project with CI, and 64 cases, each a change with a known right answer:

  • 8 pushes that break CI; the harness runs the real tests to get a real failing log;
  • 8 pull requests: 6 with a planted ML mistake and 2 clean ones;
  • 6 OpenTofu configurations;
  • 5 branch pairs to merge;
  • 15 incident reports to route;
  • 22 proposals for the Guardrail.

The expected answers were written before running the agents. The same cases were also run with every model unreachable, to measure what the LLMs add over the rule-based fallbacks.

What it showed.

  • The LLMs add the most to routing, to the Guardrail's judgement and to code review. Infrastructure and merge detection rely on graph analysis and git, so they score the same either way.
  • The failures are concrete and fixable:
    • a prompt injection in an incident report steered the router;
    • a patch that commented out the authentication middleware was auto-approved, the one unsafe decision;
    • a production model rollback that its agent labelled low needed one approver instead of two;
    • for an accuracy regression, the RCA agent copied an unrelated knowledge-base document instead of diagnosing the log.
  • Answers vary between runs, so 64 cases is a first measurement, not a final score.

Limitations

  • No user accounts yet. Who is acting is chosen in the dashboard, so the approval rules apply to names, not verified identities.
  • Nothing is written back to GitHub. Approved patches are recorded as dry runs; draft PRs and review comments are not published yet.
  • The RCA knowledge base is small. Five seed documents prove the pipeline but limit the quality of citations on unfamiliar failures.
  • A small evaluation set. The 64-case benchmark is synthetic and small; the agents have not yet been measured on real incidents from the team's repositories.
  • Partial coverage of GitHub. The app polls every 60 seconds instead of receiving webhooks, and merge and drift checks are not triggered from GitHub.
  • Local deployment only. Free model tiers have rate limits; outages are absorbed by the fallbacks.

Difficulties encountered

  • Integrating six codebases. The agents were written separately with different databases, model clients and environments. They now share one environment, one PostgreSQL database and one model client.
  • Model quirks. DeepSeek-R1 returns nothing in JSON mode, so JSON is extracted from its free-text answer instead. Hugging Face coder models did not support tool calling, so the reviewer moved to Grok. Qwen 2.5 is only served through a specific provider.
  • Calibration. The retrieval cutoff of 0.6 let irrelevant documents through; 0.3 was chosen on the seed set.
  • Missing code. A broad data/ ignore rule kept the drift agent's own package out of the repository.
